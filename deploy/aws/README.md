# AWS host component (Pulumi)

`open-workspaces-aws` is a Pulumi component package written in TypeScript. Its
`Host` component creates one EC2 instance with nested virtualization that runs
the Open Workspaces controller and runner together (single-host mode). A
[`Runner`](#runners) adds another such instance that runs only a runner and joins
a Host's controller.

What it creates:

- an EC2 instance (default `m8i-flex.xlarge`, Ubuntu 24.04) with
  `cpuOptions.nestedVirtualization = enabled`, IMDSv2 required, hop limit 1,
  and an encrypted gp3 root disk;
- a security group with **no inbound rules** (egress only);
- an IAM role and instance profile with `AmazonSSMManagedInstanceCore`,
  `ssm:GetParameter` on the host's own config parameter, and
  `secretsmanager:GetSecretValue` on the one Tailscale secret when given;
- an SSM String parameter `/open-workspaces/NAME/config` with everything the
  host applies in place (release, Tailscale, dashboard logins, images, backups,
  idle minutes). User data only bootstraps, so changing any of these updates the
  parameter and never replaces the instance;
- a separate encrypted gp3 volume formatted Btrfs and mounted at `/srv/ow`.
  It holds the sources, releases, runtime assets and workspaces, and survives
  host replacement (a new AMI or stage 0 replaces the instance, not the volume).

Every resource gets the `tags` input plus `Name`.

Direct Tailscale setup waits for DHCP routing after networkd reconfiguration.
Transient unreachable route probes retry for up to one minute; a timeout leaves
setup pending for the next `ow-host apply`.

During first boot, installing Tailscale waits up to five minutes for another
OS package process to release the dpkg frontend lock. A failed package install
still fails bootstrap; inspect `/var/log/open-workspaces-bootstrap.log`.

Operate a host (SSM shell, readiness, SSH config, stop and start with
hibernate and resume, images, backups, CI steps) with `bin/ow-aws`, and create
its backup bucket with the `ArtifactStore` component: see
[OPERATIONS.md](OPERATIONS.md).

## Use it

Versions are this repository's git tags (`vX.Y.Z`). When a new
`deploy/aws/package.json` version reaches `main`, the `aws-component-release`
workflow runs the checks, creates that tag and publishes its GitHub Release.
An existing published release is kept; an existing draft is published.
Bump `version` in the root
`Cargo.toml` and `Cargo.lock` with it (`cargo update --workspace`) so `ow --version`
reports the release, and add the release's entry to
[`release-impact.json`](../../docs/UPGRADES.md#release-impact-manifest); the
checks fail while they disagree. The same tag is the default `ref` the host
builds, so set `ref` explicitly before the first release exists.

```bash
pulumi package add https://github.com/sebassdc/open-workspaces/deploy/aws@v0.7.2
```

```typescript
import * as ow from "@sebassdc/open-workspaces-aws"; // SDK generated by `pulumi package add`

const host = new ow.Host("workspaces", {
    tags: { project: "open-workspaces" },
    // Optional: join a tailnet with an auth key stored in Secrets Manager.
    tailscaleAuthKeySecretArn: "arn:aws:secretsmanager:us-east-1:111122223333:secret:ow/tailscale-AbCdEf",
});
export const instanceId = host.instanceId;
```

| Input | Default | Notes |
| --- | --- | --- |
| `instanceType` | `m8i-flex.xlarge` | Must support nested virtualization: c8i, m8i, r8i and flex variants. |
| `subnetId` | default VPC subnet in the first zone offering the type | |
| `associatePublicIpAddress` | `true` | Egress without a NAT gateway; still no inbound rules. Use `false` with a private subnet that has NAT. |
| `amiId` | Canonical Ubuntu 24.04 x86-64 from SSM | Pin it to avoid host replacement when Canonical publishes a new image. |
| `dataVolumeSizeGib` | `100` | Btrfs volume at `/srv/ow`. |
| `repository` / `ref` | upstream repo / this package's tag | The release the host builds and runs; a change is applied in place by `ow-host upgrade` (see below). |
| `tags` | `{}` | Applied to every resource. |
| `tailscaleAuthKeySecretArn` | none | Full secret ARN; the secret string is the raw auth key. |
| `tailscaleHostname` | component name | |
| `tailscaleDirect` | none | `{ subnetId: "subnet-public" }`: secondary interface and Elastic IP for UDP 41641 only. Public subnet must be in the same VPC/AZ, with an internet gateway route. Needs `tailscaleAuthKeySecretArn`; leaves the running host in its private subnet. |
| `tailscaleSsh` | `false` | Tailscale SSH, authorized by your tailnet policy. |
| `dashboardLogins` | none | Tailnet logins allowed into the web dashboard. Needs `tailscaleAuthKeySecretArn`; see below. |
| `dashboardCapability` | none | Application capability (`example.com/cap/open-workspaces`) admitting tailnet users without a login list. Needs `tailscaleAuthKeySecretArn`. Either this or `dashboardLogins` enables the dashboard; if both are set, either admits. |
| `developerImages` | none | `["ubuntu"]`: build the [developer image](../../docs/GUEST_IMAGES.md) (user `dev`, SSH server, toolchains) after boot. SSH into boxes and golden-image recipes need it. |
| `backupUrl` | none | `s3://bucket/prefix`: install `ow-backup`, and let the host role list, read and add objects under the prefix (never delete). See below. |
| `backupSchedule` | none | When `ow-backup` runs, as a systemd calendar expression (`*-*-* 01:00:00 UTC`); the host installs a timer. Needs `backupUrl`. |
| `idleMinutes` | `30` | A box idle this long hibernates and wakes on its next connection; `0` turns it off. |

Outputs: `instanceId`, `privateIp`, `availabilityZone`, `dataVolumeId`,
`roleName`, `securityGroupId`, `configParameter`.

Every input except `instanceType`, `subnetId`, `associatePublicIpAddress`,
`amiId`, `dataVolumeSizeGib`, `tailscaleDirect` and `tags` lives in the config parameter. After
`pulumi up` changes it, apply it with `ow-aws apply` (or `ci-post-up`, which also
upgrades); the host keeps the last applied copy on its data volume.

## Reach the host

By default there are no inbound ports. SSM also works with `tailscaleDirect`:

```bash
aws ssm start-session --target "$(pulumi stack output instanceId)"
sudo ow node list      # controller view: the local runner and whether it is online
sudo ow list           # the wrapper runs every command as the `ow` user
sudo ow create my-box && sudo ow shell my-box
sudo ow node add ssh://dev@build-box   # another KVM machine as a runner
```

Two units run [single-host mode](../../docs/SINGLE_HOST.md):
`open-workspaces-worker.service` (`ow supervisor`: the worker and its VMs) and
`open-workspaces.service` (`ow host up --external-worker`: the controller and
the local runner's agent). Restarting the second leaves the VMs running. The
runner's budget is three quarters of the instance RAM, all vCPUs and 8 running
machines. Controller state lives in `/srv/ow/.ow`. The controller
listens on the host's Tailscale address (port 8790) when Tailscale is up, and on
loopback only otherwise. It picks the address at start, so the service waits up
to 60 s for Tailscale to connect first (after a reboot, for example). Workspace commands through the wrapper go to the local
runner (`/srv/ow/.ow/runner`); `node add` needs SSH access from the `ow` user.
Boxes idle for `idleMinutes` (30) hibernate and wake on the next connection; see
[wake on connect](../../docs/DAILY_USE.md). Stopping the worker unit (a worker
restart, a reboot, an instance stop or a host replacement) runs `ow down --hibernate`:
the worker refuses new starts and wakes, hibernates the running boxes, then
stops, so their processes carry on when they next wake. If a box stays running
(its capture failed), `ow down --hibernate` allows starts again, leaves the
worker running and exits non-zero; systemd then still stops the service, so on
this path that box is cold-stopped and the failure is in the journal. EC2 does not promise an instance stop that long a
shutdown window (captures run one at a time, about 25 s per 1 GiB box), so for
planned stops and replacements stop the service first and wait for it
(`ow-aws stop`, or `sudo systemctl stop open-workspaces-worker` before
`StopInstances`); the hook on the way down is the fallback. A box hibernated on a host with another kernel or
CPU (after a new AMI, say) boots its hibernated disk cold when it next starts.

With Tailscale, the host joins your tailnet under `tailscaleHostname`. The
auth key is read once at boot into a root-only file under `/run`, passed to
`tailscale up` by file reference and deleted. A failed join does not fail the
bootstrap; SSM keeps working. The Tailscale state (`/var/lib/tailscale`) is kept
on the data volume, so a replaced host (new AMI or stage 0) comes back as the
same tailnet device, with the same name and address.

## Direct Tailscale connections

By default the primary security group has no inbound rules. For a host behind
NAT, opt into `tailscaleDirect: { subnetId: "subnet-public" }`: the component
hot-attaches an interface at device index 1 with its own security group and
Elastic IP. Its only inbound rule is IPv4 UDP 41641; egress on that interface
is UDP only (peer ports vary). The primary interface and its security group,
instance inputs and user data stay identical. Device index 1 must be free.
The public subnet must route `0.0.0.0/0` to an internet gateway; allocating a
public IPv4 incurs your provider's usual charge.

After `pulumi up`, `ow-aws ci-post-up` upgrades and applies the host files in
place. Ubuntu 24.04's networkd config matches the new interface by MAC, obtains
its address and gateway by DHCP in routing table 41641, and routes only locally
originated UDP source port 41641 through it (priority 5100, before Tailscale's
rules). Other traffic keeps its primary route, DNS and NTP. A Tailscale service
drop-in pins its port to 41641; installing/removing it restarts only tailscaled
(a brief tailnet reconnect). SSH and the dashboard keep their existing tailnet
bindings; the public interface permits neither TCP service. No worker or box
is restarted. Removing the input removes these resources, policy route and
port override. Check `tailscale ping HOST` from another tailnet device for a
direct public endpoint, and `ip route get 1.1.1.1 ipproto udp sport 41641` on
the host for the secondary interface. Other peers' firewalls can still prevent
a direct connection.

## Dashboard over the tailnet

With `dashboardLogins` or `dashboardCapability`, the host also runs `open-workspaces-dashboard.service`:
`ow dashboard` on `127.0.0.1:8787` with [tailnet sign-in](../../docs/DASHBOARD.md#tailnet-sign-in),
published by `tailscale serve` to the tailnet only (never Funnel). Open
`https://HOSTNAME.TAILNET.ts.net/` as one of the listed logins. The tailnet needs
HTTPS certificates enabled (admin console, DNS). The service waits, retrying
every 30 s, until the host is on the tailnet, so a later `tailscale up` is
enough. It uses the controller root, so machines created there are placed on
the runners.

For grant-based admission, set `dashboardCapability: "example.com/cap/open-workspaces"`
and omit `dashboardLogins`. The component carries this through the in-place SSM
config and generates `allowed_capability` in the dashboard config; it does not
edit the tailnet policy. A tailnet administrator must define a user group and
destination host tag, permit HTTPS and grant that capability; see the
[policy example and revocation checks](../../docs/DASHBOARD.md#admission-through-a-capability-grant).
After the initial configuration, group/grant additions and removals require no
per-person application update, host redeploy or dashboard restart. The dashboard
checks fresh whois answers per request; terminal/SSH/preview streams recheck every 30
seconds. Revocation takes effect after policy propagation (within 35 seconds for
streams once the host sees it). An email-list fallback still admits listed users
after grant removal, so omit it for grant-only administration. Capabilities admit
users to their own catalog identity, never account-wide or host administration.

## Backups to S3

With `backupUrl`, the host gets `/usr/local/bin/ow-backup` (run it as root;
with `backupSchedule` a timer runs it). It copies the controller catalog (`ow backup catalog`) to
`PREFIX/catalog/catalog-UTCSTAMP.sqlite3`, then uploads every sealed snapshot
the store lacks (`ow backup snapshots`) to `PREFIX/snapshots/`, hibernated
boxes' captures included. It stops at the first failure and exits non-zero.

Without `backupSchedule` nothing runs it on its own: call it from your
scheduler, best right after `ow down --hibernate` (for example before a nightly
instance stop), when every running box is a sealed capture. A running box that was never snapshotted or
hibernated, and a stopped box, are not in the store.

The host role may list the bucket under the prefix and get and put objects
there; it cannot delete. Retention is the bucket's: use a private bucket with a
lifecycle rule (and versioning, so an overwrite keeps the old copy). Snapshots
hold guest memory and disks, credentials included; the catalog holds owner
identities and credential hashes.

Restore a box onto a runner (the default `ow host up` runner, or a fresh one
started with `ow --local --data-dir DIR up`):

```bash
sudo ow backup list s3://bucket/prefix/snapshots
sudo ow backup restore SNAPSHOT --from s3://bucket/prefix/snapshots [--to DIR] [--cold]
```

`backup list` names each capture's box by owner and machine name, read from the
newest catalog copy in `PREFIX/catalog/`; the last row of a box is its newest
capture.

`--cold` boots the disk when the host's CPU or kernel differs from the one that
captured it. A restored box is runner-local: reach it with
`ow --local --data-dir DIR`. Catalog restore steps are in
[core: catalog](../../docs/CORE.md#catalog).

## Boot sequence

User data (`bootstrap.sh`, stage 0) runs once per instance:

1. installs host packages and the AWS CLI v2;
2. waits for the data volume, formats it Btrfs only if it is blank, mounts it,
   and bind-mounts the Tailscale state from it;
3. creates the `ow` system user (member of `kvm`);
4. fetches the config parameter (keeping the last good copy on the volume),
   clones `repository` into `/srv/ow/src` and checks out `ref`;
5. runs that release's `deploy/aws/host/ow_host.py boot`, which stages the
   release (`scripts/setup-local.sh`: pinned Rust, Firecracker and guest assets,
   then a release build) into `/srv/ow/releases/`, pins every unit to it,
   renders the units and files (an AppArmor profile lets only release binaries
   create user namespaces), joins Tailscale, starts the worker, the control
   plane and the dashboard, then the developer-image build and the backup
   timer, and waits until the runner is online.

A data volume from a 0.4.x host is taken over: its build output moves to the
shared build directory and its assets (developer images included) seed the
first release, so nothing is downloaded or rebuilt from scratch.

Progress: `/var/log/open-workspaces-bootstrap.log`; state:
`/var/lib/open-workspaces/bootstrap-status` (`running`, `failed` or
`ok tailscale=...`). Building from source takes most of the boot time; see the
[EC2 timings](../../docs/experiments/ec2-timings.md).

## Runners

Configure the controller's private [owner limits and pool cost forecast](../../docs/LIMITS.md)
before authorizing new capacity. Unknown instance-type prices refuse invitations;
creating a cloud resource is not itself controller admission. Deployments must
supply this policy before first local-runner enrollment as well. Policy values
belong to the consuming deployment and are not guessed from a live price API.

A `Runner` is a second (usually bigger) machine for an existing Host's
controller: its own nested-virtualization instance, Btrfs data volume (kept
across replacement), role, config parameter and Tailscale identity, a worker and
a node agent, and no controller or dashboard. The component name is its node ID
(1 to 32 letters, digits, `-` or `_`).

```typescript
const host = new ow.Host("workspaces", { tailscaleAuthKeySecretArn: key, backupUrl: store.url });
const big = new ow.Runner("workspaces-2", {
    controller: { hostName: "workspaces", roleName: host.roleName },
    instanceType: "m8i.4xlarge",
    tailscaleAuthKeySecretArn: key,      // required: the controller listens on the tailnet only
    backupUrl: store.url,                // its snapshots go to backupUrl/runners/workspaces-2
    developerImages: ["ubuntu"],
});
```

It takes the Host inputs except `dashboardLogins` and `dashboardCapability`, plus `controller`: the
Host's component name and its `roleName` output (a component cannot be a
package input; in TypeScript source the Host itself fits). On top
of what a Host creates, it adds a Secrets Manager secret
`open-workspaces/NAME/join` (no value), lets its own role read and overwrite
it, and lets the controller host's role write it. Nothing else of the
controller host changes, and no other runner is touched.

Enrol it once, after `pulumi up` (`ow-aws ci-post-up` on the runner does this
by itself):

```bash
ow-aws --host workspaces runner-add workspaces-2
```

The controller host mints a single-use join file (it expires in 10 minutes)
and writes it, with its CA, into the runner's secret; the runner reads it,
stores the CA and the controller URL on its data volume, starts its node agent
and overwrites the secret once it is online. The join never passes through
the machine running `ow-aws`, and the controller gets no shell on the runner.
A replaced runner keeps its data volume, so it keeps its node credential and
comes back as the same node with its boxes; `runner-add` then only checks that
it is online. A runner whose data volume is lost cannot take its old node ID
again: `ow-aws --host workspaces runner-remove NAME` revokes it (refused while
it is online), and the new one joins under another name.

Placement, durable placement, forks on their source node and offline
handling are the controller's ([multi-node](../../docs/MULTINODE.md)):
`ow create` picks a node with room, `ow create --node workspaces-2` picks this
one, and an offline runner keeps its boxes listed while new boxes go elsewhere.
Golden images build per runner (`ow-aws --host workspaces-2 image RECIPE`).

Upgrades are the same `ow-host upgrade` on each runner, one host at a time and
the controller first: `ow-aws upgrade` on a runner passes the release its
controller runs, and the runner refuses an agent that controller would not
accept (the controller accepts its own protocol and the one before, so runners
may lag one protocol version). See [docs/UPGRADES.md](../../docs/UPGRADES.md#runners).

## Upgrades in place

Run on the host as root (`ow-aws upgrade` and `ow-aws ci-post-up` do it over SSM):

```bash
sudo ow-host upgrade --plan          # what the configured release would do; changes nothing
sudo ow-host upgrade                 # the config's release.ref
sudo ow-host upgrade v0.5.1 --max-class 1
sudo ow-host status                  # pins per unit, pending restarts, last journal
```

It fetches the ref, plans from its `release-impact.json`, builds it next to the
running releases, and moves only the units the release changed:

- a control-plane release restarts `open-workspaces.service` and the dashboard;
  boxes keep running (open SSH and terminal streams reconnect);
- a runner release drains the runner, hibernates its boxes, swaps the worker
  and wakes them; their processes continue;
- a release that changes stage 0 is refused in place: hibernate the boxes
  (`ow-aws ci-preflight`), then `pulumi up` replaces the host.

It refuses a release whose guest kernel or runtime, or this host's CPU, would
boot a box's capture cold (pass `--accept-cold` to accept that, after a backup
when `backupUrl` is set) and a class above `--max-class` (default 2). Any
failure before the pins move aborts (old worker up, boxes resumed); a failure
after rolls the pins back and verifies the old releases. A journal in
`/srv/ow/.ow/upgrade.json` lets the next run, or the next boot, finish or undo
an interrupted upgrade (`sudo ow-host recover`). To go back, upgrade to the
older tag. Details, rules and the sandbox measurements:
[docs/UPGRADES.md](../../docs/UPGRADES.md).

## Smoke test

[`examples/smoke/`](examples/smoke/) deploys a throwaway host tagged
`project=open-workspaces`, runs create, connect, snapshot, fork, live fork,
hibernate/resume and stop over SSM with timings, then always runs
`pulumi destroy`. Inputs come from the environment only, and it uses your own
Pulumi backend:

```bash
cd deploy/aws && npm ci
cd examples/smoke
export AWS_REGION=us-east-1             # plus your AWS credentials
export PULUMI_BACKEND_URL=file://$HOME/.pulumi-ow   # or your own `pulumi login`
export PULUMI_CONFIG_PASSPHRASE=...      # self-managed backends only
./run.sh
```

`run.sh` lists every variable. It only destroys a stack it created itself:
`pulumi stack init` refuses an existing `OW_STACK`, and the run stops before
touching anything. Every SSM command has a local deadline, so AWS errors end
the run and the stack is still destroyed.

## Limits

- The controller always runs on a Host, next to that Host's own runner;
  Runners only add runners. A controller-only host is a later phase.
- The host builds each release from source (first boot and every upgrade,
  about 4 minutes incremental on 4 vCPUs); there are no prebuilt release
  binaries yet.
- RAM checkpoints only restore on the same host kernel and CPU. Replacing the
  instance with a new AMI keeps disks; hibernated machines then boot their disk
  cold (their processes do not survive).
- Pulumi `destroy` deletes the data volume and every workspace on it. Protect
  the volume (`protect` resource option on the component) for long-lived hosts.

Check: `npm run check` (type check, user-data, release manifest, `ArtifactStore` and `ow-aws` tests, shellcheck when installed, then the `ow-host` Python tests; Node 22.18+, Python 3.12+).
