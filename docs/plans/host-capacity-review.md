### W7 — cached identity is sampled before waiting for the verification lock

**Actionable source finding, moderate: revalidate the opened FD after acquiring the cache lock.** `crates/ow/src/onboarding.rs:1709–1717` obtains file metadata and derives the cache key; `1719–1722` may then wait on the shared mutex held by hashing another asset. `1723` checks that earlier key, and the cache-hit path reaches `1749–1751` without a fresh fstat. The post-hash identity comparison at `1740–1743` only protects cache misses.

Concrete source interleaving: verified asset A has cached identity K; request B holds the mutex hashing another file; a request for A reads K and waits; the trusted operator rewrites/chmods A in place during that wait; B releases the mutex; A's waiting request finds cached K and serves the now changed opened file without invalidating. Unlike an immutable rename, an in-place rewrite changes bytes on that existing descriptor. This breaks the promised rewrite/metadata invalidation contract even within ordinary operator actions; no adversarial timestamp forgery is needed. Reviewer has not executed the race.

Proposed fix: obtain/check opened-file type, owner, mode, length and identity again after acquiring the cache lock and use that fresh identity for cache lookup; on a hit, fail closed if the file changed while waiting. Preserve the before/after identity check around hashing and descriptor-based serving. Proposed regression: cache A, hold verification lock with controlled asset B, wait after A's initial metadata read, same-length rewrite or chmod A, release the lock, and assert refusal/reverification rather than a stale hit. Also retain successful immutable path replacement behavior: a verified old descriptor can legitimately serve the old verified bytes while a new inode is verified independently. Any fix changes the pin and needs a narrow re-review plus matching artifact rebuild/attribution.

**W6 — full-image hashing precedes headers on every public GET and HEAD (source design concern; no measured timeout claim).** In the current moving source, `crates/ow/src/onboarding.rs:1656–1715` launches a blocking task, selects the manifest digest (`1676–1681`), opens the asset (`1692–1695`), then reads and hashes the entire asset in 64 KiB chunks (`1696–1709`) before awaiting completion and constructing either HEAD or GET response/headers (`1715–1731`). This is an explicit hash loop, rather than a call to verify_file, but has the same full-file cost. A sparse 8 GiB image still contributes every logical byte to SHA256. HEAD takes the same hash path despite sending no body. No digest/identity cache or per-asset verification concurrency bound is present in this function.

**Deadline correction:** source routing is `remote.rs:292–297` -> `dashboard.rs:175–186` -> onboarding public_download. The actual outer gateway handler deadline here is **45 seconds** (`remote.rs:273–279`), with a 64-request semaphore (`remote.rs:596`). The **10-second** middleware at `nodes.rs:651–674` covers node enrollment/control/job routes and is not shown wrapping `/cli/host/ubuntu.ext4`. Any additional deployed ingress deadline must be confirmed by core/parent configuration evidence. The handler deadline limits waiting for the Response/headers, not the subsequent full body transfer. No claim that hashing exceeds either bound on this machine is supported without measurement.

**Why this remains actionable:** the source performs O(8 GiB) hashing work per unauthenticated allowlisted request before headers. Concurrent HEADs can duplicate CPU/memory-bandwidth and cold disk/page-cache work without downloading the payload. HTTP timeout drops the wait on an already-started spawn_blocking job; there is no cooperative cancellation in the hash loop, so timed-out requests can leave expensive work running while later requests acquire released gateway permits. This is a resource-amplification design concern; severity and actual header failures remain unmeasured. Body streaming also uses a synchronous file read from poll_frame (`onboarding.rs:1631–1647`); cold GET streaming responsiveness should be included in acceptance without asserting a observed runtime stall.

**Reviewer recommendation:** preverify the selected immutable bundle once before making it available, and serve checked already-verified file handles/selection records instead of hashing the same 8 GiB for every HEAD/GET. Cache verification by bundle/manifest digest and actual opened-file identity: device, inode, logical length, nanosecond mtime/ctime, ownership/mode and relevant directory/selection identity. Check fstat on the descriptor to be served, not only a path stat followed by a separate open; verify identity before and after initial hashing. Invalidate on selection, manifest, file replacement or metadata changes; changes must fail closed or trigger one bounded verification before availability. Limit cache-miss verifications and use one shared in-flight verification per asset to prevent concurrent requests duplicating hashes; merely caching successful results after each independent hash is insufficient. Keep client-side full SHA/length checks. Metadata invalidation is an optimization within the trusted immutable operator-published artifact model, not proof against a malicious owner who can rewrite/chmod files; state that trust boundary. Do not simply omit verification for HEAD, extend the handler timeout, or trust pathname/digest metadata without establishing the selected bytes.

Do not restart/change owner services or drop shared host caches.
